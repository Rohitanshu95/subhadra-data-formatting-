# APBS 177-Character Fixed-Width File Processing & Validation System
### Final merged architecture plan

## 1. Project definition

**Objective:** a web application where an authorized user can upload APBS
response files (up to 100 files / 3 GB per batch), process them without
loading full files into memory, validate every 177-character record against
a 17-field schema, produce human-readable TXT output, track detailed
batch/file/record statistics, detect duplicate files and duplicate records,
let a human verify results before anything is committed, and — once
approved — push clean, deduplicated data into sql, safely, even if
the same files are uploaded multiple times.

This is a fixed-width parsing problem, a scale problem, and an idempotency
problem all at once. The plan below treats all three as first-class
concerns rather than bolting duplicate-detection on after the fact.

## 2. The five core problems

| # | Problem | Root cause | Solution |
|---|---|---|---|
| 1 | Huge volume | ~1 crore records/day, 300–600 files, ~20,000 records/file | Process in controlled batches (≤100 files), stream — never load a full file or full batch into RAM |
| 2 | Non-standard format | Every record is a 177-char fixed-width line, not CSV | One centralized schema definition; the parser never has ad-hoc `substring()` calls scattered through the code |
| 3 | Duplicate uploads | Re-uploading the same files (accidentally or intentionally) must not double-insert data | Three-level identity: batch → file (SHA-256) → record (SHA-256 of the normalized 177-char line) |
| 4 | Server load | A 3 GB file / 100-file batch must not blow up memory | Streaming reads, chunked processing, controlled worker concurrency |
| 5 | Database load | 1 crore individual `INSERT`s is unnecessarily expensive | Streaming + batch/bulk inserts + unique constraints + `ON CONFLICT` handling |

## 3. Field schema (177 chars / 17 fields)

| # | Field | Width | Type | Required | Notes |
|---|-------|-------|------|----------|-------|
| 1 | APBS Transaction Code | 2 | NUM | Mandatory | `77` = credit, `88` = returned transaction |
| 2 | Destination Bank IIN | 9 | NUM | Mandatory | 6-digit Destination Bank IIN |
| 3 | Destination Account Type | 2 | NUM | Optional | Account type |
| 4 | Ledger Folio Number | 3 | ALP/NUM | Optional | Alphanumeric ledger folio particulars |
| 5 | Beneficiary Aadhaar Number | 15 | NUM | Mandatory | Beneficiary's 12-digit Aadhaar Number |
| 6 | Beneficiary account holder's name | 40 | ALP/NUM | Optional | Populated only on a successful transaction |
| 7 | Sponsor Bank IIN | 9 | NUM | Mandatory | 6-digit Sponsor Bank IIN |
| 8 | User number | 7 | ALP/NUM | Mandatory | Existing User number |
| 9 | User Name / Narration | 20 | ALP/NUM | Optional | Same as INP file narration |
| 10 | User Credit reference | 13 | ALP/NUM | Mandatory | User-defined reference |
| 11 | Amount | 13 | NUM | Mandatory | Amount in paise |
| 12 | Item sequence Number | 10 | NUM | Mandatory | Allotted by NPCI |
| 13 | Checksum | 10 | NUM | Mandatory | Generated by NPCI |
| 14 | Success Flag | 1 | NUM | Mandatory | `1` = credited, `0` = returned uncredited |
| 15 | Filler | 1 | NUM | Optional | Internal use |
| 16 | Reason Code | 2 | NUM | Mandatory | Reason for not crediting |
| 17 | Destination Bank account number | 20 | ALP/NUM | Optional | Populated only if successful |

Non-credit lines (header/trailer records, e.g. transaction code `33`) are
detected and skipped — not treated as parse failures.

## 4. Duplicate detection architecture

This is the most important part of the design, and it operates at three
levels:

```
FILE
 │  SHA-256 of file content
 │  Exact duplicate? ──YES──▶ SKIP (mark DUPLICATE_FILE, don't reprocess)
 │              └──NO──▶ PROCESS
 ▼
RECORD
 │  SHA-256 of the normalized 177-char line
 │  Already exists (in this batch, another batch, or already in SQL)?
 │              ├─YES──▶ mark DUPLICATE, don't insert
 │              └─NO───▶ INSERT
```

- **File identity:** every uploaded file gets a SHA-256 hash of its content
  (not its filename). Same content under a different filename is still
  recognized as the same file and skipped without reprocessing.
- **Record identity:** file hashing alone isn't enough — two files can
  overlap by only some records. Every valid parsed record also gets
  `record_hash = SHA256(normalized_177_char_record)`, enforced as a SQL
  `UNIQUE` constraint at commit time. This catches the same transaction
  appearing in a different file, a different batch, or a different upload
  session entirely.
- **Exact vs. business duplicate:** an exact duplicate is a byte-identical
  177-char record — that's what `record_hash` catches, and it's what the
  first production version implements. A *business/logical* duplicate is
  two records representing the same transaction with a cosmetic field
  difference (e.g. `ROHIT` vs `ROHIT KUMAR`) — these have different hashes
  and require an explicit business key to detect. The 177-char spec alone
  doesn't tell us what that key should be, so: **ship exact-duplicate
  detection first, keep business-key logic as a configurable, confirmed
  addition later** rather than guessing at it now.

Partial-duplicate example: batch of 100 files / 2,000,000 records where
1,800,000 are new and 200,000 already exist → only 1,800,000 reach the
database; the other 200,000 are logged as duplicates, not silently dropped
and not treated as errors.

## 5. System architecture

```
React (Vite) UI
   │  upload · batch status · progress · statistics · results · logs
   ▼  HTTPS
Nginx reverse proxy
   ▼
FastAPI  ──  auth · upload validation · batch management · REST + WebSocket
   │
   ├──────────────┐
   ▼              ▼
Job queue      sql
(Celery+Redis)  (batches, files, transactions, duplicates_log, logs)
   │
   ▼
Controlled worker pool
   │  streaming read → SHA-256 → 177-char parse → 17-field validation
   │  → record hash → normalized TXT output
   ▼
File storage (input / output / errors / logs, per batch)
```

**Why Celery + Redis specifically for the "job queue":** it gives
independently scalable workers, per-task retries, and a monitoring surface
(Flower) for free, without hand-rolling a worker pool. Worker concurrency is
a config value, not a hard-coded number — start conservative (e.g. 4
concurrent file-workers) and tune based on observed CPU/I/O load.

## 6. Complete batch workflow

1. **User opens the app** — UI states the limits up front: max 100 files,
   max 3 GB/batch, 177-char record format, TXT output.
2. **User selects files** — client-side pre-check (file count ≤ 100,
   combined size < 3 GB); this is a UX convenience, not the source of
   truth.
3. **Create batch** — FastAPI generates a batch ID (e.g.
   `BATCH-20260820-001-8F3A`), status = `CREATED`.
4. **Stream upload** — files are streamed directly to
   `/data/input/BATCH-.../`, never buffered whole in the API process; SHA-256
   is computed during the stream, not as a separate re-read pass.
5. **File duplicate check** — hash looked up against the `files` table.
   Found → `DUPLICATE_FILE`, skipped. Not found → `READY`, queued.
6. **Enqueue & process** — batch moves `QUEUED` → `PROCESSING`; a controlled
   number of workers each take one file at a time.
7. **Streaming read** — each worker reads the file incrementally
   (line-by-line / chunked), never loading the whole file into memory,
   regardless of whether it's 20,000 or 2,000,000 records.
8. **Record length check** — `len(line) == 177`? No → log
   `INVALID_RECORD_LENGTH` with the line number and continue; one bad line
   never stops the file.
9. **Parse 17 fields** — fixed offsets from the single schema definition
   (§3), not scattered substring calls.
10. **Field validation** — numeric fields checked for format (transaction
    code, amount, success flag, etc.); invalid records are logged and
    counted, not silently accepted.
11. **Record hash + normalized output** — valid records get a
    `record_hash` and are written to
    `/data/output/BATCH-.../fileNNN_output.txt` in the specified delimited
    format.
12. **Running statistics** — records read / valid / invalid / duplicate /
    output are tracked continuously per file, not computed only at the end.
13. **File completion** — file status → `COMPLETED`; worker picks up the
    next file.
14. **Batch completion** — once all files are done, generate a
    `batch_summary.txt` and final counts; batch status →
    `COMPLETED` or `COMPLETED_WITH_ERRORS` (partial failure is not the same
    as total failure — see §9).
15. **Verify (human checkpoint)** — the user reviews the summary, sample
    records, and downloadable TXT/error reports **before** anything touches
    production data. This is the step that protects against a bad batch
    getting silently committed.
16. **Commit to database** — on explicit approval, the import service
    streams the output records, checks `record_hash` against the existing
    `UNIQUE` constraint, and bulk-inserts only the new ones. Duplicates are
    written to `duplicates_log`, not dropped without a trace.
17. **Dashboard** — aggregated, real-time view (via WebSocket/SSE) of batch
    progress, and a historical view of completed batches, success/failure
    rates, and duplicate counts over time.

## 7. Storage layout

```
storage/
├── input/
│   └── BATCH-001/
│       ├── file001.txt
│       └── ...
├── output/
│   └── BATCH-001/
│       ├── file001_output.txt
│       └── ...
├── errors/
│   └── BATCH-001/
│       ├── file001_errors.txt
│       └── ...
└── logs/
    └── BATCH-001/
        ├── batch_summary.txt
        ├── batch.log
        ├── files.log
        └── errors.log
```

Every batch is independently traceable. Input files are not kept forever —
apply a configurable retention policy (delete/archive input after output is
validated and the retention window passes), decided as an explicit business
policy given the sensitivity of the data, not hard-coded.

## 8. Database schema

**batches** — id, batch_uuid, user_id, created_at, started_at,
completed_at, total_files, total_size, total_records, valid_records,
invalid_records, duplicate_records, status

**files** — id, batch_id, filename, size, sha256, record_count,
valid_records, invalid_records, duplicate_records, status, input_path,
output_path, error_path, created_at, completed_at

**transactions** (production, post-verification) — id, record_hash
(`UNIQUE`), batch_id, file_id, and all 17 parsed fields, created_at

**duplicates_log** — id, record_hash, attempted_batch_id, attempted_file_id,
original_transaction_id, reason, detected_at

**logs** — id, batch_id, file_id (nullable), level, message, timestamp

Bulk insert with `ON CONFLICT (record_hash) DO NOTHING` (or an explicit
conflict-logging variant) is the mechanism, not row-by-row `INSERT`.

## 9. Failure handling hierarchy

A single bad record must not stop a 20,000-record file. A single bad file
must not stop a 100-file batch. Only genuine infrastructure failure stops a
batch outright.

```
Record failure → continue file
File failure    → continue batch
Batch failure   → only on system/infrastructure failure
```

Example: 100 files, 99 completed, 1 failed → batch status
`COMPLETED_WITH_ERRORS`, not `FAILED`.

## 10. Logging architecture (four tiers)

- **application.log** — API start/stop, logins, batch created, worker
  start/stop, system-level errors
- **batch.log** — batch created, files uploaded, processing started/completed
- **files.log** — per file: filename, size, sha256, record counts (total /
  valid / invalid / duplicate), output size, duration, status
- **errors.log** — invalid file, invalid record, invalid length, parser
  error, output error, database error

**No sensitive values in any log.** Aadhaar and account numbers are masked
everywhere except the actual protected data store —
`Aadhaar: ********9012`, `Account: *******3456` — and ideally not logged in
full at all unless a specific, justified need exists.

## 11. Security requirements

Given the data includes Aadhaar numbers, names, and bank account details:

- HTTPS everywhere; authentication + authorization (JWT-based sessions)
- File size limits, file count limits, file-type validation, path-traversal
  protection on upload
- Masked identifiers in the UI and in all logs; no PII in application logs
- Controlled/authenticated download endpoints
- Temporary file cleanup and a defined retention policy
- Full audit trail: who created a batch, who verified it, who approved the
  commit, who downloaded output
- Rate limiting on upload and API endpoints

## 12. Performance strategy

Avoid, categorically:
- Loading an entire file into RAM
- Loading all 100 files of a batch into RAM at once
- One database query per record
- Processing all 300–600 files of a day simultaneously
- Storing raw PII in application logs
- Using filename (rather than content hash) for duplicate detection

Instead: streaming I/O, a bounded worker pool, and bulk database writes.
CPU cost of parsing a fixed-width line is trivial — the real constraints are
upload bandwidth and database write throughput, both of which streaming +
bulk insert address directly.

## 18. Locked design decisions

| Requirement | Design |
|---|---|
| Frontend | React.js + Vite |
| Backend | FastAPI |
| Task queue | Celery + Redis |
| Input | Fixed-width TXT, 177 chars, 17 fields |
| Batch limits | ≤100 files, ≤3 GB |
| Processing | Streaming, controlled worker concurrency |
| Output | TXT (one output file per input file) |
| Errors | Separate TXT per file |
| File duplicate detection | SHA-256 of content |
| Record duplicate detection | SHA-256 of normalized record |
| Human verification | Required before DB commit |
| Database | sql |
| DB duplicate protection | `UNIQUE(record_hash)` + `ON CONFLICT` |
| Progress updates | WebSocket/SSE |
| Logs | Application + batch + file + error, PII-masked |
| Deployment | Docker + Nginx |
| Security | JWT auth, HTTPS, masked PII, audit trail, rate limiting |

## 19. Build order (recommended)

1. Vertical slice: single-file upload → stream-parse → TXT output → log —
   prove the parser and streaming approach end to end.
2. Batch upload (up to 100 files) + file-level SHA-256 duplicate detection.
3. Job queue integration (Celery + Redis) with controlled worker
   concurrency, replacing synchronous processing.
4. Record-level hashing + verification screen (human checkpoint) before any
   database write.
5. sql schema + bulk-insert import service with
   `UNIQUE(record_hash)` conflict handling.
6. Dashboard, WebSocket live progress, historical batch view.
7. Security hardening pass (auth, masking, audit trail, rate limiting) and
   retention-policy implementation.

The critical principle throughout: **idempotency**. Whether the same file
or transaction is uploaded 2, 5, or 10 times, the system must recognize it
and never blindly create duplicate records — at the file level, the record
level, and the database level.

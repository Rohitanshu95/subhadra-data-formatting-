# Refined Implementation Plan: 177-Character Record Separator & Headings Skip

## Problem Statement & Understanding

### Current Project Behavior
- In the existing backend ([StreamingValidator](file:///c:/Users/rohitanshu.dhar/Desktop/projects/data-separator-/backend/app/services/validation.py)), files are read line-by-line (`for line_no, raw_line in enumerate(infile)`).
- This assumes that input files have newlines (`\n` or `\r\n`) between records and starts validating transactional data from the very first line.
- If an uploaded file has no newlines, Python reads the entire file as a single line, causing length mismatch errors.

### The New Data Format & Requirements
- **Unorganized continuous character stream**: Incoming files do NOT have newlines separating records.
- **Record 1 (Characters 1 to 177)**: Contains the **headings** (header record). **Confirmed: This record MUST BE SKIPPED** from transaction validation and not written as a data row to the clean output file.
- **Record 2 (Characters 178 to 354)**: Starts at character 178 (index 177, 0-based), which is the 1st character of the first data record, spanning exactly 177 characters.
- **Record 3 (Characters 355 to 531)**: Starts at character 355, spanning 177 characters.
- **Subsequent Records**: Every 177 characters is a distinct record to be separated, parsed into the 17-field schema, validated, and routed to clean output or errors.
- **Memory Safety**: Files must be processed in a streaming fashion (chunked buffer) so large files do not load all characters into RAM.
- **Dual Support**: Automatically support both continuous streams (no newlines) and legacy newline-delimited files.

## Technical Architecture & Design

```
Raw Uploaded Stream
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│             Streaming Record Separator                      │
│  - Inspects file format (continuous stream vs newline-del.) │
│  - Yields 177-character records streamingly                 │
└─────────────────────────────────────────────────────────────┘
       │
       ├─► Record 1 (Chars 1..177)  ──► [HEADINGS ROW] ──► SKIP (Increment skipped_lines, log info)
       │
       ├─► Record 2 (Chars 178..354) ──► Data Record 1 ──► Parse 17 fields ──► Validate ──► Output / Error
       │
       ├─► Record 3 (Chars 355..531) ──► Data Record 2 ──► Parse 17 fields ──► Validate ──► Output / Error
       │
       └─► Record N                  ──► Data Record N-1 ──► Parse 17 fields ──► Validate ──► Output / Error
```

## User Review & Decisions

> [!IMPORTANT]
> **Confirmed User Decisions:**
> 1. **Record 1 (Headings) Handling**:
>    - The first 177 characters are recognized as the headings row and **strictly skipped**.
>    - It is counted under `skipped_lines` (in file metadata and summary reports).
>    - It is logged in the console: `[STREAM PARSER] [HEADER] Record 0001: Headings row detected (177 chars) -> Skipped`.
>    - It will NOT fail numeric validation or generate false error logs.
> 2. **Data Record Extraction**:
>    - Record 2 begins at character 178 (length 177) and is the first transactional record.
>    - Every subsequent 177-character slice is processed as a separate record.
> 3. **Output File Consistency**:
>    - The clean output file (`_output.txt`) will continue to receive the standard pipe-delimited schema headers generated by `OutputWriter`, followed by all valid parsed data records.
>    - The database importer, summary generator, and dashboard previews remain 100% compatible.

## Proposed Changes

### Backend Processing Pipeline

#### [NEW] [record_separator.py](file:///c:/Users/rohitanshu.dhar/Desktop/projects/data-separator-/backend/app/services/record_separator.py)
Create a dedicated streaming record separator service:
- `stream_apbs_records(file_handle, record_length=177, buffer_size=65536)`:
  - Generator that yields `(record_number, record_string)`.
  - **Auto-Detection**:
    - Peeks at the initial content to determine whether records are delimited by newlines (`\n` or `\r\n`) or packed as a continuous fixed-width stream.
  - **Continuous Stream Mode**:
    - Reads fixed chunks of 177 characters.
    - Yields `record_number = 1` for characters 1..177 (headings).
    - Yields `record_number = 2` for characters 178..354 (data record 1).
    - Strips/ignores optional trailing newlines/carriage returns between blocks if present.
    - If a trailing partial record remains at EOF (< 177 chars), yields it so the validator can flag it as `INVALID_RECORD_LENGTH`.
  - **Newline-Delimited Mode**:
    - Yields lines stripped of `\r\n` with line numbers (preserving 100% compatibility with existing test files and legacy inputs).

#### [MODIFY] [validation.py](file:///c:/Users/rohitanshu.dhar/Desktop/projects/data-separator-/backend/app/services/validation.py)
Update `StreamingValidator.process_file`:
- Replace `for line_no, raw_line in enumerate(infile, start=1)` with `stream_apbs_records(infile, record_length=self._record_length)`.
- **Heading Skip Logic**:
  - For `record_no == 1`:
    - Check if it represents the headings row (or header transaction '33'):
    - Increment `result.skipped_lines += 1`.
    - Log: `[PARSER] [SKIP] Record 0001: Headings record skipped`.
    - Continue to Record 2 (char 178 onwards).
  - For `record_no >= 2`:
    - Perform length validation (expected 177).
    - Parse 17 fixed-width fields using `parse_line()`.
    - Validate fields using `validate_fields()`.
    - Write clean records to `OutputWriter` and errors to `ErrorWriter`.
- Update summary logging to explicitly report the skipped heading record.

#### [MODIFY] [apbs_parser.py](file:///c:/Users/rohitanshu.dhar/Desktop/projects/data-separator-/backend/app/services/apbs_parser.py)
- Add a helper function `is_heading_or_header_line(line: str, record_no: int = 1) -> bool` to reliably identify header/heading records by transaction code ('33') or textual/non-numeric field headings in record 1.
